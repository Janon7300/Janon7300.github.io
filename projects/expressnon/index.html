THE PROBLEM 01

Sharing a file
often creates another copy.

Email has limits. Chat leaves an attachment behind. Cloud drives add uploads, accounts, permissions, and cleanup before a nearby device receives anything.

OLD FLOWUpload → wait → share → download → delete

The service becomes a warehouse even when users only need a temporary bridge.

RETHINK
EXPRESSNONMeet → connect → send directly

The room is a rendezvous point, not storage for the payload.

PRODUCT FLOW 02

One short code.
Four clear moments.

No account setup and no complicated room link. The interface keeps the technical handshake behind a six-character code.

  1. 01Choose

    Select up to 20 files / 100 MB, or paste text and code.

  2. 02Create

    Choose 1–5 recipients and create a six-character room code.

  3. 03Connect

    The receiver enters the code while temporary signaling introduces both browsers.

  4. 04Transfer

    WebRTC carries the payload directly, with progress visible for each recipient.

ENGINEERING 04

The difficult part begins
after “connect.”

01 · STREAMChunk without freezing

Payloads are split into 16 KB chunks. A buffered-amount high-water mark applies backpressure instead of filling browser memory without control.

02 · MULTI-PEEROne room, independent receivers

Each of the 1–5 recipients gets an individual connection, state, and progress path so one slow peer does not hide everyone else's status.

03 · LIFECYCLETemporary by default

Codes expire after ten minutes, the sender stays present during transfer, and cleanup removes stale signaling metadata.

04 · FAILURETimeouts users can understand

Connection and signaling timeouts turn network uncertainty into visible states: connecting, queued, sending, done, or failed.

SECURITY 05

Protect the meeting point.
Keep the payload out.

The security story is layered and specific. It avoids promising that peer-to-peer means invulnerable.

EDGECSP + security headers

Restrictive content, frame, referrer, permission, isolation, and HTTPS policies reduce the browser attack surface.

REQUESTOrigin + size validation

Same-origin checks, JSON-only requests, and an 8 KB body ceiling reject malformed API traffic early.

IDENTITYAnonymous Auth + App Check

Clients prove an app session without adding a signup wall to the product flow.

ABUSEIP + UID rate limits

Upstash counters protect ingress and actions. Production fails closed if the limiter is unavailable.

ROOMBounded membership

One to five receiver slots, short expiry, and random transfer tokens limit room lifetime and reuse.

DATANo payload storage

Firestore and Storage deny all because neither service is used as a file bucket.

HONEST BOUNDARIES 06

Privacy has limits.
Say them clearly.

Good product communication includes what the architecture cannot guarantee, not only what it does well.

01STUN is not universal

Some enterprise, campus, or strict NAT networks may need a TURN relay, so a connection is not guaranteed everywhere yet.

02The sender stays online

Because there is no uploaded copy waiting on a server, the sender's browser must remain open until recipients finish.

03Recipients can keep data

Peer-to-peer limits server storage; it cannot stop an intended recipient from saving or forwarding what they receive.

04The browser is not antivirus

Users still need to trust the sender and scan suspicious files. Transport privacy is not content safety.
